# 1. Общие сведения

Система – веб-сайт «Rewatch», сервис, представляющий собой универсальный инструмент для ведения списков фильмов, сериалов, аниме и мультфильмов. Перечень типов медиа хранится в справочнике и может расширяться (например, играми, книгами, комиксами). В отличие от существующих решений, ориентированных на один тип медиа, Rewatch объединяет их в едином пространстве, позволяя пользователям отмечать желаемое и просмотренное, выставлять оценки, вести статистику и отслеживать прогресс.

Заказчиком и исполнителем выступает Леснов Семён Алексеевич.

## 1.1. Основание для пересмотра ТЗ

Версия 1.x предполагала прототип на Python (Flask). В рамках дисциплины «Веб-программирование» проект переносится на следующий стек:

- серверная часть на **PHP** с использованием фреймворка **Laravel**;
- клиентская часть на **React** с использованием фреймворка **Next.js**;
- база данных **SQLite**.

Функциональные требования системы при переносе не сокращаются, изменяются архитектура, технологии реализации и требования к инфраструктуре.

## 1.2. Плановые сроки и стоимость

Этапы работ, сроки и стоимость определяются календарным планом проекта и актуализируются при переносе (приложение к ТЗ). Постоянные расходы на инфраструктуру: домен (около 1300 руб./год), хостинг на собственном сервере, объектное хранилище S3 (Yandex Object Storage, на момент написания – бесплатный тариф).

# 2. Назначение и цели создания системы

Система предназначена для автоматизации процесса формирования статистики потреблённого медиа пользователей по их требованиям.

Цели создания системы с точки зрения заказчика и пользователей:

- Сформировать библиотеку кинематографа с возможностью добавления пользователями новых медиа.
- Предоставить возможность сортировать медиа по спискам, создавать собственные списки и делиться ими с другими пользователями.
- Создать расширенную систему статусов, заметок и оценок.
- Обеспечить необходимые инструменты для добавления, удаления и редактирования медиа в базе данных сервиса.

# 4. Архитектура системы

## 4.1. Общая схема

```
                Пользователь (браузер)
                         │  HTTPS
                         ▼
                ┌─────────────────┐
                │      Nginx      │  обратный прокси, TLS
                └───────┬─────────┘
          /api/*        │        всё остальное
       ┌────────────────┴────────────────┐
       ▼                                 ▼
┌──────────────────┐            ┌──────────────────┐
│ Laravel (PHP-FPM)│  ◄─ HTTP ─ │  Next.js (Node)  │
│  REST API        │            │  React-интерфейс │
└───┬─────┬────┬───┘            └──────────────────┘
    │     │    │
    │     │    └──► Queue worker + Scheduler (импорт, фоновые задачи)
    │     │
    │     └──► S3-хранилище (постеры, фото персон)
    ▼
 SQLite (файл .sqlite, WAL) ──► Litestream ──► облачное хранилище (реплика)

Внешние системы: TMDb, AnimeDB, Telegram Bot API, SMTP-сервер
```

## 4.2. Подсистемы

1. **Backend (Laravel)** – бизнес-логика, REST API, авторизация, модерация, интеграции с внешними системами, фоновые задачи.
2. **Frontend (Next.js)** – пользовательский интерфейс и панель модератора. Публичные страницы (каталог, страница медиа, публичные списки) рендерятся на сервере для скорости загрузки и индексации поисковыми системами. Приватные страницы (личные списки, профиль) работают как клиентские.
3. **База данных (SQLite)** – единый файл базы данных на локальном SSD сервера.
4. **Файловое хранилище (S3)** – постеры и фото; в базе хранятся только ключи объектов.
5. **Фоновые процессы** – обработчик очереди (импорт из TMDb, отправка писем и Telegram-уведомлений) и планировщик (ночные резервные копии, очистка).

## 4.3. Взаимодействие

- Клиент и API работают на одном домене: запросы `/api/*` Nginx направляет в Laravel, остальные – в Next.js. Это позволяет использовать cookie-авторизацию Sanctum без настройки CORS между разными доменами.
- Формат обмена – JSON по REST, версия API в префиксе `/api/v1`.
- Загрузка постеров выполняется через API; Laravel проверяет формат и размер, приводит изображение к соотношению 2:3 и сохраняет в S3.
- Внешние базы данных опрашиваются только по запросу пользователя (форма поиска) или модератора (автоматическое наполнение); результат в основную таблицу медиа напрямую не пишется.

## 4.4. Ограничения SQLite и план роста

- SQLite допускает одну одновременную запись. Для заявленной нагрузки (раздел 5.1) это допустимо при настройках: `journal_mode=WAL`, `busy_timeout=5000`, `foreign_keys=ON`, `synchronous=NORMAL`.
- Файл базы находится на локальном SSD, не на сетевой файловой системе.
- Доступ к данным выполняется только через Eloquent и миграции Laravel, без SQLite-специфичного SQL, кроме модуля полнотекстового поиска. При превышении нагрузки возможен переход на PostgreSQL заменой драйвера в конфигурации и переносом данных.

# 5. Требования к аппаратным и программным ресурсам хостинга

## 5.1. Допущения по нагрузке (MVP)

| Параметр                                  | Значение                     |
|-------------------------------------------|------------------------------|
| Зарегистрированных пользователей          | до 500                       |
| Одновременных активных сессий             | до 50                        |
| Пиковая нагрузка на API                   | до 20 запросов/с             |
| Записей медиа в каталоге                  | до 20 000                    |
| Размер постера после обработки            | до 200 КБ (соотношение 2:3)  |
| Доступность                               | 24/7, редкие профилактические остановки |

Значения являются расчётными допущениями и уточняются по метрикам после запуска.

## 5.2. Оценка потребления оперативной памяти

| Компонент                                   | Оценка, ГБ   |
|---------------------------------------------|--------------|
| ОС (Ubuntu Server 24.04 LTS)                | 0,3 – 0,5    |
| Docker Engine                               | 0,1 – 0,2    |
| Nginx                                       | до 0,05      |
| PHP-FPM (5–8 воркеров по 40–70 МБ)          | 0,3 – 0,5    |
| Next.js (Node.js, режим `standalone`)       | 0,25 – 0,5   |
| Queue worker + Scheduler                    | около 0,1    |
| **Итого**                                   | **1,2 – 2,0**|

Сборка Next.js (`next build`) кратковременно требует около 1,5–2 ГБ. Сборку рекомендуется выполнять на машине разработчика или в CI и переносить готовые Docker-образы на сервер; при сборке на самом сервере необходим swap не менее 2 ГБ.

## 5.3. Требования к серверу

| Ресурс             | Минимальные                  | Рекомендуемые                     |
|--------------------|------------------------------|-----------------------------------|
| Процессор          | 1 vCPU / 2 ядра x86-64 или ARM64 | 2 vCPU / 4 ядра                |
| Оперативная память | 2 ГБ (+ swap 2 ГБ)           | 4 ГБ                              |
| Диск               | 30 ГБ SSD                    | 60 ГБ SSD (NVMe или SATA)         |
| Сеть               | 50 Мбит/с                    | 100 Мбит/с, проводное подключение |
| Трафик             | до 100 ГБ/мес (оценка)       | без ограничений                   |

Расчёт объёма диска:

| Статья                                           | Объём         |
|--------------------------------------------------|---------------|
| ОС и образы Docker                               | 15 – 20 ГБ    |
| Код и зависимости (vendor, Next.js standalone)   | 1 – 2 ГБ      |
| База SQLite (20 000 медиа, 500 пользователей)    | до 1 ГБ       |
| Логи (с ротацией)                                | 1 – 2 ГБ      |
| Локальные резервные копии (7–14 штук)            | 5 – 10 ГБ     |

Постеры хранятся не на сервере, а в S3: 20 000 × ~150 КБ ≈ 3 ГБ.

## 5.4. Программное обеспечение сервера

- ОС: Ubuntu Server 24.04 LTS (или иной Linux с поддержкой Docker).
- Docker Engine и Docker Compose.
- Контейнеры: Nginx, PHP-FPM (PHP 8.2+, расширения `pdo_sqlite`, `sqlite3`, `mbstring`, `intl`, `gd` или `imagick`, `curl`, `zip`), Node.js (LTS-версия, поддерживаемая выбранной версией Next.js), процесс Queue worker, процесс Scheduler (cron).
- Litestream для репликации SQLite.
- Certbot (Let's Encrypt) или иной механизм выпуска TLS-сертификатов.
- Настроенный файрвол (открыты порты 80, 443 и SSH только для администратора).

## 5.5. Сетевые требования

- Домен (около 1300 руб./год) с A-записью на сервер.
- Постоянный внешний IP-адрес. Если провайдер выдаёт динамический адрес или блокирует входящие порты 80/443, используется DDNS либо туннель (например, Cloudflare Tunnel).
- HTTPS обязателен на всех страницах.
- Для домашнего сервера, работающего 24/7: источник бесперебойного питания (ИБП), проводное подключение Ethernet.

## 5.6. Внешние сервисы

| Сервис                              | Назначение                                           |
|-------------------------------------|------------------------------------------------------|
| S3-хранилище (Yandex Object Storage)| Постеры, фото персон, реплика базы данных            |
| TMDb API (и AnimeDB)                | Поиск и импорт данных о медиа                        |
| Telegram Bot API                    | Уведомления и интеграция с ботом                     |
| SMTP-сервер                         | Письма подтверждения регистрации и восстановления пароля |

## 5.7. Резервное копирование

- Непрерывная репликация SQLite в S3 средствами Litestream.
- Ночная копия базы командой `sqlite3 .backup` с хранением 7–14 последних копий.
- Резервное копирование файла `.env` и конфигураций контейнеров в защищённое хранилище (не в публичный репозиторий).
- Проверка восстановления из резервной копии не реже одного раза за этап разработки.

## 5.8. Среда разработки

- Компьютер разработчика: 8 ГБ ОЗУ и более, свободно 10 ГБ на диске.
- PHP 8.2+, Composer 2, Node.js LTS, Git, Docker Desktop.
- Локальная версия проекта запускается командой `docker compose up`; для файлов используется MinIO вместо облачного S3.

# 6. Требования к системе

## 6.1. Требования к структуре и функционированию

- Описание подсистем и их взаимодействия приведено в разделе 4.
- Система взаимодействует с внешними системами (сторонние базы данных, Telegram Bot) посредством API по необходимости.
- Система должна быть доступна 24/7 с редкими профилактическими остановками.

## 6.2. Требования к численности и квалификации персонала

- Заказчик единолично имеет полный доступ ко всем возможностям системы.
- В качестве дополнительного персонала могут выступать модераторы базы данных и модераторы франшиз.
- Модератор базы данных должен уметь работать с CRUD-операциями и понимать принципы работы с медиа.
- Модератор франшиз должен быть компетентен в рамках выбранной им франшизы.
- Требований к режиму работы персонала нет.

## 6.3. Требования к безопасности

- Пароли хранятся только в виде хэшей (bcrypt или Argon2 средствами `Hash` Laravel).
- Для регистрации требуется электронная почта с подтверждением адреса.
- Защита от CSRF (Sanctum), ограничение частоты запросов (rate limiting) на авторизацию и создание контента.
- Валидация всех входных данных на сервере; HTML заметок очищается от опасных тегов перед сохранением и выводом.
- Файл `.env`, ключи API и доступы к S3 не хранятся в репозитории.
- Файл базы данных находится на защищённом сервере с периодической репликацией в облачное хранилище (раздел 5.7).
- Доступ к панели модерации только для ролей «модератор» и «администратор».

# 7. Функциональные требования

Все действия, изменяющие общую базу медиа, проходят модерацию.

## 7.1. Создание нового медиа

- Любой авторизованный пользователь может создать новое медиа.
- Поля формы: название на русском; название на английском; оригинальное название; описание на русском; постер; дата первого выхода; тип медиа (из списка); серия (франшиза); жанры (минимум один); компании с ролями (необязательно); персоны с ролями (необязательно).
- Если нужной серии (франшизы), компании или персоны нет, их можно создать в этом же окне: название серии и компании – латиницей, для персоны – имя; для серии можно указать родительскую серию.
- Система проверяет заполнение обязательных полей (все, кроме компаний и персон) и выводит сообщение об ошибках.
- Форму можно заполнить автоматически через поиск по внешним базам данных (указываются название и тип медиа, система выводит совпадения, пользователь выбирает нужное и проверяет заполненные данные).
- Корректно заполненная запись передаётся на модерацию.

## 7.2. Редактирование существующего медиа

- Любой пользователь может предложить изменения любого существующего медиа.
- Форма аналогична форме создания, но без поиска по внешним базам.
- Изменения отправляются на модерацию; без модерации запись в базе не меняется.
- Модератор видит заявки в панели администратора, проверяет их и принимает или отклоняет.

## 7.3. Добавление медиа в списки пользователя

- Пользователь находит медиа через строку поиска на странице нужного типа в профиле и добавляет его в свой список, указав дату, статус и общую оценку (если тайтл просмотрен).
- Если медиа не найдено, система предлагает создать его в базе.
- При обнаружении некорректных данных пользователь может перейти к редактированию медиа.

## 7.4. Просмотр списков медиа

- По умолчанию списки отсортированы по дате добавления от новых к старым.
- Списки по разным типам медиа отображаются на отдельных страницах профиля в виде таблиц.
- Доступны сортировка и фильтрация (по дате, статусу, оценке).

## 7.5. Редактирование и удаление записей в списках

- Пользователь может изменить дату, статус и оценку добавленного медиа и удалить любое медиа из своих списков.
- Пользователь может создать собственный список, сделать его открытым или закрытым и поделиться им по ссылке.

## 7.6. Оценки

- Десятибалльная шкала.
- Оценка выставляется как всему медиа, так и каждому эпизоду сериала отдельно.

## 7.7. Заметки

- Личная заметка к любому медиа и к каждому эпизоду отдельно.
- Редактор поддерживает форматирование текста (списки, начертание и т. п.).

## 7.8. Прогресс просмотра

- Эпизоды сериалов отмечаются просмотренными по отдельности; система показывает прогресс по тайтлу.

## 7.9. Дополнительные возможности пользователя

- Поиск медиа в базе сервиса.
- Случайный фильм или сериал из всей базы или среди выбранных критериев.
- Статистика (количество просмотренных медиа, распределение по жанрам и статусам).
- Импорт и экспорт данных пользователя.

## 7.10. Наполнение базы данных

- База в основном наполняется пользователями вручную либо с помощью поиска по внешним базам данных.
- **(Дополнительно)** Автоматическое наполнение через API внешних баз или парсеры запускается строго вручную модератором в панели администратора. Собранные данные автоматически в базу не записываются и попадают в очередь модерации.

## 7.11. Работа с франшизами (дополнительно)

- Просмотр списка и страниц франшиз.
- Модерация страницы франшизы модератором франшиз.

# 9. Модель данных системы

Термины: «серия (франшиза)» – группа связанных медиа (например, Dexter); «эпизод» – отдельная серия сериала.

| Сущность             | Основные атрибуты                                                                              | Связи                                                     |
|----------------------|------------------------------------------------------------------------------------------------|-----------------------------------------------------------|
| Пользователь         | имя, логин, электронная почта, пароль (хэш), роль, язык, тема                                  | 1 – N отмеченных медиа, списков                           |
| Медиа                | название (ru), название (en), оригинальное название, описание, ключ постера, дата выхода, статус модерации | N – 1 тип, N – 1 серия, N – M жанры, компании, персоны |
| Тип медиа            | название                                                                                       | 1 – N медиа                                               |
| Серия (франшиза)     | название, родительская серия                                                                   | иерархия; 1 – N медиа. Серия без родителя – франшиза      |
| Жанр                 | название                                                                                       | N – M медиа                                               |
| Компания             | название                                                                                       | N – M медиа (с ролью)                                     |
| Персона              | имя, ключ фото                                                                                 | N – M медиа (с ролью)                                     |
| Роль                 | название                                                                                       | используется в связях медиа–компания и медиа–персона      |
| Статус               | название (желаемое, смотрю, просмотрено, пересмотрено, заброшено)                              | 1 – N отмеченных медиа                                    |
| Эпизод               | медиа, сезон, номер, название                                                                  | N – 1 медиа                                               |
| Отмеченное медиа     | пользователь, медиа, статус, дата, оценка, заметка                                             | N – 1 пользователь, медиа, статус                         |
| Отмеченный эпизод    | отмеченное медиа, эпизод, просмотрено, оценка, заметка                                         | N – 1 отмеченное медиа, эпизод                            |
| Пользовательский список | пользователь, название, признак открытости, ссылка для доступа                              | N – M медиа                                               |
| Заявка на модерацию  | автор, медиа (или новые данные), тип (создание / изменение), состав изменений, статус, модератор, комментарий | N – 1 пользователь, медиа                  |

Схема создаётся миграциями Laravel; в таблицах используются внешние ключи, индексы по внешним ключам и по полям поиска и таблица FTS5 для названий медиа.

# 11. Интерфейс системы

- Поддержка светлой и тёмной темы (переключение в интерфейсе, тема запоминается в профиле).
- Два акцентных цвета, каждый используется для своих задач.
- Логотип выполнен в градиентной цветовой гамме (изображение логотипа передаётся в приложении к ТЗ).
- Цвета и отступы задаются CSS-переменными, что позволяет менять тему без переписывания компонентов.
- Постеры отображаются в соотношении 2:3.
- Тексты интерфейса хранятся в файлах переводов (русский, английский).

# 12. Программный интерфейс (REST API)

Базовый префикс: `/api/v1`. Формат: JSON. Авторизация: Laravel Sanctum. Полное описание генерируется в формате OpenAPI.

| Метод и путь                                        | Назначение                                      | Доступ           |
|-----------------------------------------------------|-------------------------------------------------|------------------|
| `POST /auth/register`, `/auth/login`, `/auth/logout`| Регистрация, вход, выход                        | гости / все      |
| `GET /auth/me`                                      | Текущий пользователь                            | авторизованные   |
| `GET /media`                                        | Поиск, фильтры, сортировка, пагинация           | все              |
| `GET /media/{id}`                                   | Карточка медиа                                  | все              |
| `GET /media/random`                                 | Случайное медиа по критериям                    | все              |
| `POST /media`                                       | Создание медиа (заявка на модерацию)            | авторизованные   |
| `PUT /media/{id}`                                   | Предложение изменений (заявка на модерацию)     | авторизованные   |
| `GET /external/search`                              | Поиск во внешних базах (TMDb и др.)             | авторизованные   |
| `GET /reference/{genres,types,statuses,roles}`      | Справочники                                     | все              |
| `GET/POST /franchises`, `/companies`, `/persons`    | Поиск и создание связанных сущностей            | авторизованные   |
| `GET/POST/PATCH/DELETE /me/entries`                 | Отмеченные медиа пользователя                   | авторизованные   |
| `PATCH /me/entries/{id}/episodes/{episode}`         | Прогресс, оценка и заметка по эпизоду           | авторизованные   |
| `GET/POST/PATCH/DELETE /me/lists`                   | Пользовательские списки                         | авторизованные   |
| `GET /lists/{id}`                                   | Публичный список                                | по настройке     |
| `GET /me/stats`                                     | Статистика                                      | авторизованные   |
| `GET /me/export`, `POST /me/import`                 | Экспорт и импорт данных                         | авторизованные   |
| `GET /moderation/requests`                          | Очередь заявок                                  | модераторы       |
| `POST /moderation/requests/{id}/approve` / `reject` | Принять или отклонить заявку                    | модераторы       |
| `POST /admin/import/run`                            | Запуск автоматического наполнения (дополнительно) | модераторы     |
